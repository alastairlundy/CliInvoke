# Decision Ledger — CliRun Shape

Topic: deepening candidate **F4** — `CliRun`'s dead `_externalProcessFactory` field and the 6 near-identical `Run*Async` bodies. Sessions recorded in this ledger reshape `CliRun` so the field is read and the bodies funnel into one internal method.

Scope: decisions in this ledger affect `src/CliInvoke/Extensions/CliRun.cs` and any test files added under `tests/CliInvoke.Tests/` to cover the static façade.

Cross-references:
- Domain glossary: `CONTEXT.md` (notably the `Resource-Owning Type` definition; `CliRun` is a static façade over `Resource-Owning Type`s).
- File-path-resolver ADR: `docs/decisions/DECISIONS-CliInvoke-file-path-resolver-seam.md` (**not yet present in the working tree** — cited forward-looking; T014 double-check locking on `_filePathResolver` and D008 asymmetry of `UseFilePathResolver` vs `UseExternalProcessFactory` will be recorded in that ledger when it is created; flagged per the reviewer's issue 9).
- F1 ledger: `docs/decisions/DECISIONS-CliInvoke-process-invocation-pipeline.md` (the pipeline collapse is upstream of F4 and shapes how the internal method is named).
- F2 ledger: `docs/decisions/DECISIONS-CliInvoke-process-configuration-shape.md` (irrelevant to F4 — `CliRun` consumes `ProcessConfiguration` from the public 3-param ctor side, not the protected 15-param ctor side; the F2 amendment that T001 originally called for is **no longer required** because T006 reverted pre-resolution, so the slot remains the resolution mechanism).

### [D001] — disposition of the dead `_externalProcessFactory` field

- **Resolved Answer**: "Option 1" (in context: "Option 1 — Honour the field").
- **Normalized Requirement**: `_externalProcessFactory` shall be honoured as the live configuration surface that `UseExternalProcessFactory` was meant to set. The 6 `Run*Async` bodies shall funnel into a single private internal method that calls `GetExternalProcessFactory()` rather than constructing `new ExternalProcessFactory(resolver)` directly. The `UseFilePathResolver` setter (locked per T014) and the `UseExternalProcessFactory` setter (intentionally unlocked per D008) keep their current asymmetry.
- **Constraints**: T014's double-check locking on `_filePathResolver` is preserved. D008's asymmetry (the factory setter is unlocked by design) is preserved. The public API surface is binary-compatible: signatures are unchanged, no types are added or removed. Behaviour is changed per T005 (default factory construction is per-call, not lazy) and T006 (helper is pure, resolution happens at the factory level); see those records for the behaviour deltas. The factory seam is real once D001 is honoured: two adapters exist (the static default `() => new ExternalProcessFactory()` and any caller-supplied factory), so the seam is real, not hypothetical.

### [D002] — shape of the internal funnel method

- **Resolved Answer**: "I agree with the shape" (referring to the generic-with-delegate form: `RunInternalAsync<T>(ProcessConfiguration, ProcessExitConfiguration?, Func<IExternalProcess, CancellationToken, Task<T>>, CancellationToken)`).
- **Normalized Requirement**: The private internal method shall be `static async Task<T> RunInternalAsync<T>(ProcessConfiguration configuration, ProcessExitConfiguration? exitConfiguration, Func<IExternalProcess, CancellationToken, Task<T>> capture, CancellationToken cancellationToken)`. Each of the 3 `ProcessConfiguration`-arg public overloads (`RunAsync`, `RunBufferedAsync`, `RunPipedAsync` at `src/CliInvoke/Extensions/CliRun.cs:129, 189, 257`) becomes a one-line forward: `RunInternalAsync(cfg, exit, (p, t) => p.<CaptureMethod>(t), ct)`. The internal method routes through `GetExternalProcessFactory()` (per D001) and uses `ProcessExitConfiguration.CreateGraceful()` as the default when `exitConfiguration` is null.
- **Constraints**: The 3 `IExternalProcess` capture methods (`WaitForExitOrTimeoutAsync` returns `ProcessResult`, `CaptureBufferedResultAsync` returns `BufferedProcessResult`, `CapturePipedResultAsync` returns `PipedProcessResult`) define the three `T` instantiations; the type parameter is inferred at each of the 3 call sites. The 3 string-arg overloads (`RunAsync`, `RunBufferedAsync`, `RunPipedAsync` at lines 97, 164, 224) keep their own bodies for now — they each build a `ProcessConfiguration` and `ProcessExitConfiguration` from string args before calling the config overload. A separate branch decides whether the 3 string-arg overloads' shared 5-line config-building step is also collapsed.

### [D003] — the 3 string-arg overloads' 5-line config-building step

- **Resolved Answer**: "Option 2" (in context: "Option 2 — Extract a private BuildStringArgsConfig helper, called by all 3 string overloads").
- **Normalized Requirement**: A new private static method `BuildStringArgsConfig(string targetFilePath, string arguments, string? workingDirectory, bool redirectStandardOutput, TimeSpan? timeoutTimeSpan, out ProcessExitConfiguration exitConfiguration) : ProcessConfiguration` shall be added to `src/CliInvoke/Extensions/CliRun.cs`. Each of the 3 string-arg overloads (`RunAsync` at line 97, `RunBufferedAsync` at line 164, `RunPipedAsync` at line 224) shall call the helper and then call the matching config overload with the returned `ProcessConfiguration` and the `out ProcessExitConfiguration`. The redirect-output flag passed to `ProcessConfigurationFactory.Create` becomes an explicit parameter: `false` for `RunAsync`, `true` for `RunBufferedAsync` and `RunPipedAsync`, making the asymmetry between the non-redirecting and redirecting factories visible at each call site.
- **Constraints**: The helper's signature uses `out ProcessExitConfiguration` as the default; a separate branch (D004) decides whether to swap that for a tuple or record return. The 5-line config-building block (lines 101–109, 168–176, 228–236 in the current file) is deleted from each string overload; the equivalent logic lives once in the helper. `IFilePathResolver` is **not** read inside the helper — it stays in `GetFilePathResolver()` per the F1-leakage analysis; the helper is a pure transformation from string args to `ProcessConfiguration` + `ProcessExitConfiguration`.

### [D004] — shape of the `BuildStringArgsConfig` return

- **Resolved Answer**: "Option 2" (in context: "Option 2 — Tuple return `(ProcessConfiguration Configuration, ProcessExitConfiguration ExitConfiguration)`").
- **Normalized Requirement**: The helper's signature shall be `private static (ProcessConfiguration Configuration, ProcessExitConfiguration ExitConfiguration) BuildStringArgsConfig(string targetFilePath, string arguments, string? workingDirectory, bool redirectStandardOutput, TimeSpan? timeoutTimeSpan)`. Each of the 3 string-arg overloads in `src/CliInvoke/Extensions/CliRun.cs` (lines 97, 164, 224) shall destructure with `var (configuration, exitConfiguration) = BuildStringArgsConfig(...);` and then call the matching config overload. The redirect-output flag (`false` for `RunAsync`, `true` for `RunBufferedAsync` and `RunPipedAsync`) is the only difference between the three call sites and is visible at the call site.
- **Constraints**: `Supersedes: D003` on the helper's return shape (the `out ProcessExitConfiguration` parameter pattern in D003 is replaced by the tuple return) and on the `IFilePathResolver` reading (D003's "helper is a pure transformation" rule is updated — the helper does read the resolver via `GetFilePathResolver()`). The tuple element names (`Configuration`, `ExitConfiguration`) travel at the call site, not in the helper's signature; a future rename in the helper's tuple definition can drift from the call-site destructures unless a unit test exercises the end-to-end flow. The helper stays `private static`; the tuple return type is not promoted to a public record.

### [D005] — F4 vs F1 (the Process Invocation Pipeline) relationship

- **Resolved Answer**: "Option 1" (in context: "Option 1 — F4 is independent; F1 absorption is a follow-up").
- **Normalized Requirement**: F4 ships as designed by D001–D004 without introducing `ProcessInvocationContext` or any other F1 type. `CliRun.RunInternalAsync<T>` (D002) and `CliRun.BuildStringArgsConfig` (D003, D004) live in `src/CliInvoke/Extensions/CliRun.cs` as private static members. F1's `ProcessInvocationPipeline` is built separately per `docs/decisions/DECISIONS-CliInvoke-process-invocation-pipeline.md#D001` and `#D002`. When F1 ships, a follow-up edit rewrites `RunInternalAsync<T>`'s body to construct a `ProcessInvocationContext` and call `_pipeline.ExecuteAsync(context, capture, cancellationToken)`; the public surface of `CliRun` (the 6 `Run*Async` methods, the 2 `Use*` setters) is unchanged.
- **Constraints**: The F1 follow-up is a 5-line edit on `RunInternalAsync<T>` plus adding a field for the `ProcessInvocationPipeline` (per F1 D001, the pipeline is `internal` to `CliInvoke`, so no assembly-boundary change). A comment at the top of `RunInternalAsync<T>` shall point at `docs/decisions/DECISIONS-CliInvoke-process-invocation-pipeline.md#D001` and the pipeline module, so a future contributor adding a 4th `Run*` capture mode routes through `_pipeline.ExecuteAsync` instead of re-duplicating the skeleton. F4 does not lock the F1 D002 decision about whether `ProcessInvocationContext` is mutable or immutable — that decision is F1's to make.

### [T001] — BuildStringArgsConfig resolver reading

- **Resolved Answer**: "Option 2 — Helper reads the resolver eagerly."
- **Normalized Requirement**: `BuildStringArgsConfig` shall call `GetFilePathResolver()`, resolve `targetFilePath` up-front via the resolver, and write the resolved `FileInfo.FullName` into `ProcessConfiguration.TargetFilePath` before returning. The funnel does not need to read the resolver; the executor's `StartAsync` write to the slot becomes a no-op for `CliRun`-built configs. The custom resolver registered via `UseFilePathResolver(customResolver)` is honored — the helper reads the same static getter the funnel would have read.
- **Constraints**: `Supersedes: D003` (on resolver reading — D003 said the helper is a pure transformation that does not read `IFilePathResolver`; T001 contradicts that and matches D004's "the helper does read the resolver via `GetFilePathResolver()`" line). Requires a follow-up amendment to `DECISIONS-CliInvoke-process-configuration-shape.md` D001 and D013 to allow eager resolution as a legitimate pattern for `CliRun` callers. F2 D001/D013's "TargetFilePath is the resolution slot written to at execution time" stays valid for direct `IProcessInvoker` callers that don't pre-resolve; the slot is no longer load-bearing for `CliRun`-built configs. The redirect-output flag (`false` for `RunAsync`, `true` for `RunBufferedAsync` and `RunPipedAsync`) is the only difference between the three call sites and is unaffected by the resolver read. Resolution failures (e.g., `FileNotFoundException` for an unresolvable path) surface at the public `Run*Async` call site rather than inside `IExternalProcess.StartAsync`; the stack trace shifts but the exception type is preserved.
- **Cites**: D002, D004 (F4 ledger); cross-cite: F2 D001, D013 of `DECISIONS-CliInvoke-process-configuration-shape.md` (requires amendment).

### [T002] — ExternalProcessFactory construction

- **Resolved Answer**: "Option 1 — Lazy default factory via `Lazy<T>`."
- **Normalized Requirement**: The default `ExternalProcessFactory` shall be wrapped in a `static readonly Lazy<IExternalProcessFactory> _defaultFactory` field. The `_externalProcessFactory` delegate at `src/CliInvoke/Extensions/CliRun.cs:23-24` shall be initialized to `() => _defaultFactory.Value` instead of `() => new ExternalProcessFactory()`. The default factory (and its internal `FilePathResolver` allocated by the parameterless ctor at `src/CliInvoke/Factories/ExternalProcessFactory.cs:30-33`) is constructed once on first access; subsequent `GetExternalProcessFactory()` calls reuse the singleton. The custom-factory path is unaffected — `UseExternalProcessFactory(customFactory)` continues to override the delegate and returns the same custom factory each call.
- **Constraints**: A comment at the `_defaultFactory` declaration shall read "constructed on first access; do not reset" so a future contributor does not refactor the field initializer back to a per-call `new ExternalProcessFactory()`. The change is local to `src/CliInvoke/Extensions/CliRun.cs`; no other file is touched. `Lazy<T>` adds a small per-access indirection on the default path; the custom-factory path is unchanged from the current code. The `IsAotCompatible=true` and `<IsTrimmable>true</IsTrimmable>` settings in `src/CliInvoke/CliInvoke.csproj` are unaffected — `Lazy<T>` is AOT-friendly in .NET 8+.
- **Cites**: D001 (F4 ledger).

### [T003] — test strategy for the pre-resolution path and lazy factory

- **Resolved Answer**: "Option 1 — Public-surface tests with a custom resolver."
- **Normalized Requirement**: Tests shall be added under `tests/CliInvoke.Tests/` (a new file, e.g., `tests/CliInvoke.Tests/CliRunTests.cs`) that exercise the public `CliRun` surface only. Each test registers a custom `IFilePathResolver` via `UseFilePathResolver` and a custom `IExternalProcessFactory` via `UseExternalProcessFactory`; tests assert (a) the throw from an unresolvable path happens at the public call site, not inside `IExternalProcess.StartAsync`; (b) the resolved path flows into `Configuration.TargetFilePath`; (c) the custom factory's `CreateExternalProcess` is invoked exactly once per `Run*Async` call (verifying the lazy default factory is not constructed when a custom factory is registered). The pre-resolution path is verified by a resolver that throws — the throw type is the resolver's, not the factory's, so the resolution happens before `IExternalProcess.StartAsync` is reached. No `InternalsVisibleTo` changes are needed; `BuildStringArgsConfig` and `RunInternalAsync<T>` stay `private static`.
- **Constraints**: The throw-timing assertion is the load-bearing check — a regression that defers resolution back to `StartAsync` would still satisfy a "throw type" assertion but fail the "throw happens before factory call" assertion. The custom factory used in tests must implement a counter (or the test must assert `CreateExternalProcess` call count) to verify the lazy default factory is not constructed. Existing tests under `tests/CliInvoke.Tests/Invokers/ProcessInvokerTests.cs` cover `IProcessInvoker` end-to-end; the new `CliRun` tests are additive, not replacements. Test infrastructure should reset the `CliRun` static state between tests (TUnit `[BeforeEach]` hooks call `UseExternalProcessFactory(new ExternalProcessFactory())` and `UseFilePathResolver(new FilePathResolver())` to clear any cross-test contamination).
- **Cites**: T001, T002, D002, D005 (F4 ledger).

### [T006] — BuildStringArgsConfig resolver reading (T001-revised)

- **Resolved Answer**: "Option 1 — Revert T001 to deferred resolution; helper is pure; funnel does resolution via the factory's resolver."
- **Normalized Requirement**: `BuildStringArgsConfig` shall **not** call `GetFilePathResolver()` and shall **not** pre-resolve. The helper builds a `ProcessConfiguration` with the raw user-supplied `targetFilePath` (per D003's pure-helper plan). The funnel calls `factory.CreateExternalProcess(cfg, exit)`; the factory's resolver resolves the path at `IExternalProcess.StartAsync` (per F2 D001/D013). The factory owns the resolver; both string-arg and config-arg overloads route through the factory, so the asymmetric precedence flagged by the reviewer is resolved. The `UseFilePathResolver(customResolver)` setter continues to flow into the default factory via T005's `() => new ExternalProcessFactory(GetFilePathResolver())` delegate.
- **Constraints**: `Supersedes: T001` (T001 mandated pre-resolution in the helper, which created asymmetric precedence when a custom factory with a different resolver was registered — the string-arg path used the static resolver while the config-arg path used the factory's resolver; T006 reverts to deferred resolution so the factory is the single source of resolution). The F2 amendment to `DECISIONS-CliInvoke-process-configuration-shape.md` D001/D013 that T001 called for is **no longer required** — the slot remains the resolution mechanism for `CliRun`-built configs, consistent with F2's documented contract. The helper is pure (D003's plan); the funnel does the resolver-aware construction via the factory. A code-review note at the top of `BuildStringArgsConfig` shall read "T006: helper is pure; resolution happens at the factory level; do not pre-resolve in the helper" so a future contributor does not re-add pre-resolution. The fail-fast behaviour of pre-resolution is sacrificed for symmetric precedence; users who want early validation can call `IFilePathResolver.TryResolveFilePath` directly before invoking `Run*Async`. T001's `Cites:` line's cross-reference to F2 D001/D013 is withdrawn.
- **Cites**: D003, D004, T001, T005 (F4 ledger).

### [D006] — BuildStringArgsConfig return shape (D004-revised)

- **Resolved Answer**: "Option 1 — Revert D004 to D003's `out ProcessExitConfiguration` parameter pattern."
- **Normalized Requirement**: The helper signature shall be `private static ProcessConfiguration BuildStringArgsConfig(string targetFilePath, string arguments, string? workingDirectory, bool redirectStandardOutput, TimeSpan? timeoutTimeSpan, out ProcessExitConfiguration exitConfiguration)`. The 3 string-arg overloads (`RunAsync` at `src/CliInvoke/Extensions/CliRun.cs:97`, `RunBufferedAsync` at line 164, `RunPipedAsync` at line 224) shall call the helper with the `using var` pattern: `using var configuration = BuildStringArgsConfig(targetFilePath, arguments, workingDirectory, redirectStandardOutput: false, timeoutTimeSpan, out var exitConfiguration);` and then forward to the matching config-arg overload. The `using` declaration applies to the disposable `ProcessConfiguration`; the `out` parameter receives the auxiliary `ProcessExitConfiguration`. - **Constraints**: `Supersedes: D004` (D004's tuple return is fragile per the reviewer's issues 4 and 5 — named tuple element names do not propagate across the method boundary and can drift from call-site destructures on rename, and the tuple destructure breaks the `using var` declaration syntax, forcing a nested `using` block or a separate `using var` after the destructure). The redirect-output flag (`false` for `RunAsync`, `true` for `RunBufferedAsync` and `RunPipedAsync`) remains the only difference between the three call sites and is visible at each call site. The D004 normalized requirement's destructuring pattern (`var (configuration, exitConfiguration) = BuildStringArgsConfig(...);`) is replaced by the `out` pattern. The D004 constraints' "tuple element names travel at the call site" risk is moot — the parameter name lives in the signature.
- **Cites**: D003, D004 (F4 ledger).
