# Decision Ledger — file-path resolver seam

> Grilling session for architecture-review candidate **C2**: make the file-path resolver seam real.
> Generated: 2026-07-01.

> Numbering gaps at T002, T009, and T011 are intentional — see T016 for the rationale.

### [D001] — static `FilePathResolver.Shared` fate

- **Resolved Answer**: "(1) Let's delete the static singleton"
- **Normalized Requirement**: `FilePathResolver.Shared` shall be removed from the public API; every consumer (`ExternalProcess` constructors, `ExternalProcessFactory` constructor, `CliRun` factory lambda) shall require an `IFilePathResolver` instance with no default fallback.
- **Constraints**: v3 is in development and not released; breaking changes to the public API are permitted without a deprecation cycle or `CliInvoke.Legacy` shim package. `docs/architecture.md:125` (which currently documents the static fallback as expected behaviour) shall be updated in the same change. No future contributor shall reintroduce a static convenience method (`Default`, `Instance`, etc.) without a new decision record.

### [D002] — `CliRun` resolver source

- **Resolved Answer**: "(1) Is much better UX but the name needs renaming. To align with the ExternalProcessFactory method name, I think 'UseFilePathResolver' is a suitable name"
- **Normalized Requirement**: `CliRun` shall expose a static `UseFilePathResolver(IFilePathResolver resolver)` configuration method; the existing `_externalProcessFactory` lambda shall thread the configured resolver through to `ExternalProcessFactory.CreateExternalProcess`; `AddCliInvoke` shall invoke `CliRun.UseFilePathResolver` with the DI-resolved `IFilePathResolver` so DI users get zero call-site boilerplate.
- **Constraints**: The method shall be named `UseFilePathResolver` to align with the existing `CliRun.UseExternalProcessFactory` naming convention. Configuration before use shall be required — the failure mode for an unconfigured `CliRun` call shall be a loud exception (e.g., `InvalidOperationException` with a message naming the missing configuration call), never a silent `null` resolver at the call site.

### [D003] — `IFilePathResolver` failure semantics

- **Resolved Answer**: "(2) I guess we can adopt but I don't foresee future first party fall-back callers"
- **Normalized Requirement**: `IFilePathResolver` shall gain a `bool TryResolveFilePath(string filePathToResolve, out FileInfo? resolvedFilePath)` method alongside the existing `FileInfo ResolveFilePath(string filePathToResolve)` method; the throwing method's contract is unchanged; a successful resolution sets `resolvedFilePath` to the `FileInfo` and returns `true`; a failure sets `resolvedFilePath` to `null` and returns `false` without throwing.
- **Constraints**: The user does not anticipate future first-party fall-back callers beyond the current `ShellDetector` use case. The `Try*` method is added for that single first-party caller plus any future third-party implementer; `IFilePathResolver` is not expected to grow further `Try*` methods without a new decision record. The breaking change for custom `IFilePathResolver` implementers (one extra method) is accepted.

### [D004] — `ResolverBase` / `Resolver` method distribution

- **Resolved Answer**: "(C) although GetPathInfo will need a new name now that it's an explicitly documented protected method in a public abstract class. GetPathExtensionsInfo may be worth renaming to drop the 'Info' suffix and possibly renaming to 'GetPathFileExtensions' to clarify it's meaning."
- **Normalized Requirement**: `IFilePathResolver` shall be implemented by a `public abstract class FilePathResolverBase` (the contract) and a `public class FilePathResolver : FilePathResolverBase` (the default). `FilePathResolverBase` declares the data accessors as `protected virtual` (concrete, overridable) and the strategies as `protected abstract`. `FilePathResolver` implements the two abstract strategies and inherits the data accessors. `GetPathExtensionsInfo` shall be renamed to `GetPathFileExtensions`. A new name for `GetPathInfo` shall be chosen in a follow-up branch.
- **Constraints**: The data accessors are `protected virtual`, not `protected`, so a future custom-PATH resolver can override them without breaking the abstract method signatures. The strategies are `protected abstract`, forcing the adapter author to think about the resolution order. The rename of `GetPathExtensionsInfo` to `GetPathFileExtensions` follows the user's naming convention (drop the "Info" suffix, use a plural noun that names the return value). The `GetPathInfo` rename shall follow the same naming convention (parallel structure with `GetPathFileExtensions`).

### [D005] — `GetPathInfo` rename

- **Resolved Answer**: "Option 2 - This isn't inconsistent with the Get method since they return different types. the Get method returns an array and the Enumerate methods returns a IEnumerable<string>?. Both are idiomatic for their return types. The asymmetry isn't wrong in this instance because the File Path Extensions are a known quantity for Unix and involves multiple enumeration in the implementation - The alternative is having each ResolverBase implementer call .ToArray internally to satisfy the symmetry."
- **Normalized Requirement**: The current `protected virtual IEnumerable<string>? GetPathInfo()` shall be renamed to `protected virtual IEnumerable<string>? EnumeratePathDirectories()`. The `Get`-prefix is reserved for fixed-size returns (arrays) where the result is a known quantity; the `Enumerate`-prefix is used for `IEnumerable<T>` returns where the implementation may involve multiple internal enumerations.
- **Constraints**: The asymmetry with `GetPathFileExtensions` (which returns `string[]`) is intentional and reflects the .NET convention of matching verb to return type. ResolverBase implementers shall not be required to call `.ToArray()` to satisfy Get-prefix symmetry; the asymmetry is a feature, not a debt. The convention (Get for arrays, Enumerate for IEnumerable) shall be documented in `CONTEXT.md` so future contributors do not "fix" the asymmetry.

### [D006] — `GetPathInfo` rename (refined rationale)

- **Resolved Answer**: "To clarify, for multiple enumerations - I meant that Multiple enumeration is inevitable with the File extensions but doing this is computationally expensive. An array being accessed multiple times is computationally cheaper than multiple lookups on an enumerable."
- **Normalized Requirement**: The current `protected virtual IEnumerable<string>? GetPathInfo()` shall be renamed to `protected virtual IEnumerable<string>? EnumeratePathDirectories()`. The asymmetry with `GetPathFileExtensions` (which returns `string[]`) is performance-driven: `GetPathFileExtensions`'s implementation performs multiple internal enumerations — one per candidate file extension when testing a bare name like `dotnet` — each of which is computationally expensive; materialising the result into an array gives the caller O(1) re-access. `EnumeratePathDirectories` does not have this concern, so it remains a lazy `IEnumerable<string>?`.
- **Constraints**: The naming convention is performance-driven, not just type-driven: `Get`-prefix for arrays (when the caller is expected to re-access and re-iteration would be expensive); `Enumerate`-prefix for `IEnumerable<T>` (when re-iteration is cheap or unlikely). This convention shall be documented in `CONTEXT.md` so future contributors do not "fix" the asymmetry. `Supersedes: D005`.

### [D007] — `FilePathResolverBase` package boundary

- **Resolved Answer**: "Option 2 - Move to Core. If it stayed in base CliInvoke it would be less useful to other Resolver implementations and force main package dependency to implement a custom Resolver (analogous but not identical to the problem we are solving)."
- **Normalized Requirement**: `FilePathResolverBase` shall live in `CliInvoke.Core` alongside `IFilePathResolver`; the concrete `FilePathResolver` stays in `CliInvoke`. Third-party Resolver implementations shall be able to extend the base without depending on the main `CliInvoke` package.
- **Constraints**: This introduces a new pattern in `CliInvoke.Core` (abstract base classes alongside interfaces); the pattern shall be applied consistently in future modules with analogous shape (interface in Core, abstract base that captures a shared algorithm in Core, concrete in main package). The abstract base's method order in `ResolveFilePath` is a maintained contract — refactors that want to reorder or merge the two strategy methods are constrained and require a new decision record.

### [T001] — algorithm placement in `FilePathResolverBase`

- **Resolved Answer**: "Option 1 - TryResolveFilePath should be a wrapper. FileNotFound exception counts as not found. But by convention Try methods don't throw exceptions AT ALL."
- **Normalized Requirement**: `FilePathResolverBase.ResolveFilePath` shall contain the public algorithm and call the two `protected abstract` strategies in the documented order. `FilePathResolverBase.TryResolveFilePath` shall be a wrapper: `try { resolvedFilePath = ResolveFilePath(filePathToResolve); return true; } catch (Exception) { resolvedFilePath = null; return false; }`. The wrapper must not propagate any exception.
- **Constraints**: The `catch` is `Exception`, not `FileNotFoundException`, because the .NET `Try*` convention forbids throwing. `FileNotFoundException` is the only exception type the current `ResolveFilePath` body intentionally throws (from `LocateFileFromDirectory`); the broader catch is required by convention, not by algorithm. Concrete resolvers extending the base implement exactly the two `protected abstract` strategies and inherit the public methods — the count of abstract methods on the concrete stays at two. Lossy `false` semantics (e.g., a transient `IOException` flattened to "not found") are accepted; the wrapper is not required to surface partial-failure reasons to the caller. `ShellDetector`'s Windows fallback chain (try `pwsh.exe`; on failure, try `cmd.exe`) migrates by replacing the `try`/`catch` with `if (!TryResolveFilePath("pwsh.exe", out var pwsh))` — the `false` return is the single signal the chain needs.
- **Cites**: D001, D003, D004, D007

### [T005] — `GetPathFileExtensions` casing strategy

- **Resolved Answer**: "Option 2 makes sense and string manipulation can be expensive."
- **Normalized Requirement**: `FilePathResolverBase.GetPathFileExtensions` shall return lowercased extensions. The strategy loop in `ResolveFromPathEnvironmentVariable` shall use them as-is, with no per-iteration `.ToLower()`. The base's default implementation (which calls `PathEnvironmentVariable.GetPathFileExtensions()`) shall lowercase the array in a single pass before returning. Custom resolvers overriding `GetPathFileExtensions` must return lowercased extensions; this contract shall be documented in `CONTEXT.md`.
- **Constraints**: Custom resolvers that violate the contract (return raw extensions) produce a silent runtime bug — symptom is "no match found" for a case that should match. The contract is documented in `CONTEXT.md` to reduce the chance of violation. The performance rationale follows D006's "Get for arrays, Enumerate for IEnumerable" — both choices push the cost (materialisation in D006's case, lowercasing here) to the producer (base) rather than the consumer (loop). On Windows, the path-extension loop iterates `(number of PATH entries) × (number of extensions)` times; with `PATH` sizes that routinely exceed 50 entries and 5+ extensions on developer machines, the per-iteration `.ToLower()` cost is real.
- **Cites**: D004, D005, D006

### [T014] — `UseFilePathResolver` optionality and lazy default (with lock)

- **Resolved Answer**: "Option 4 - I want thread safety."
- **Normalized Requirement**: The static `CliRun` shall have a `private static IFilePathResolver? _filePathResolver` field (default `null`) and a `private static readonly object _syncRoot = new()` lock object. `UseFilePathResolver(IFilePathResolver resolver)` shall validate the argument (throw `ArgumentNullException` on `null`) and assign the field under `lock(_syncRoot)`. Each `Run*` method shall call a private `GetFilePathResolver()` helper that double-checks the field (read outside the lock for the hot path) and, if `null`, constructs `new FilePathResolver()` under `lock(_syncRoot)` and caches it. The constructed default is reused for the process lifetime.
- **Constraints**: `Supersedes: T003`. The loud-failure rule is dropped — there is no `InvalidOperationException` for "not configured." The single-lock design creates an asymmetric sync pair with the existing `UseExternalProcessFactory` (which has no lock at `src/CliInvoke/Extensions/CliRun.cs:32`); the asymmetry shall be documented in `CONTEXT.md` so reviewers do not "fix" it by removing the lock or by adding a lock to `UseExternalProcessFactory`. `UseFilePathResolver(null)` shall not leave the field in a "configured with null" state. The double-check pattern keeps the hot path lock-free; the lock is acquired only on the first `Run*` call after process start (or after a configuration change, if the field is briefly cleared by a future contributor). The originally-asked T011 T-record (error shape) is moot and was never recorded.
- **Cites**: D001, D008, D009, T003
